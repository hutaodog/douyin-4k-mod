# 18-PC 补丁 v1.1 定稿：为什么"自动选最高档"最后是靠"什么都不做"

> 这一轮折腾了 8 个版本，最后发现**正确解法是把我们自作聪明的部分全删掉**。
> 本文记录三次弯路和最终结论，避免以后再踩。

---

## 一、最终形态（v1.1）

补丁只做四件事：

| # | 做什么 | 位置 |
|---|---|---|
| 1 | 把 `sessionStorage['MANUAL_SWITCH']` 写成 `{gearType:-2, gearClarity:'20', gearName:'超清 4K'}` | 隔离世界，每 400ms 幂等写一次 |
| 2 | 改写服务端 AB 配置里的"自动降档/自动重选清晰度"开关 | 主世界，fetch/XHR 响应改写 |
| 3 | 钉住编码族（h264）+ 拦截 4K 项被抽走 | 主世界，播放器 `changeDefinition` |
| 4 | 让客户端底部清晰度标签跟上真实解码分辨率 | 主世界，纯改文字 |

**不加**：按高度自动降档、播放中强制切流、自动 reload、按播放器列表改目标。

---

## 二、结论：客户端自己就会"取该视频的最高档"

79 个采样点（时间 / 播放器档位 / 实际解码 / 该视频档位表最高档）：

| 时间 | `cur`（播放器） | 实际解码 | 该视频档位表最高档 | 一致性 |
|---|---|---|---|---|
| 07:52:51 | -2 | 3840×2160 | -2 | ✅ |
| 07:53:33 | -2 | 2160×3840（竖屏 4K） | -2 | ✅ |
| 07:54:15 | -1 | 2560×1440 | -1 | ✅ |
| 07:54:27 | -2 | 3840×2160 | -2 | ✅ |
| 07:55:27 | 2 | 960×720 | 2 | ✅ |
| 07:56:15 | -2 | 3840×2160 | -2 | ✅ |

**规律**：`cur` 与该视频档位表能提供的最高档完全对应；**档位表里没有 4K 时，客户端会自己 clamp 到列表最高档**（不会硬降到 720）。

所以我们只要把目标钉在 4K，最终效果天然就是"该视频能给的最高画质"。

## 三、三次弯路（都是"过度设计"）

### 弯路 1：用"当前解码高度"判断该不该降档

```js
if (videoHeight < 2000) → 判定"没有 4K" → 把目标降到 2K
```

**错在哪**：客户端起播时常常先从 1440 起播再往上爬。用"瞬时高度"当判据，等于把"正在爬升"误判成"没有更高档"，
结果我们亲手把 4K 拉成 2K。日志证据：`step-down h=1440 < 2000` 之后客户端再也没上去。

**正确判据**：看这条视频**档位表里有没有那一档**，不是看此刻解码多高。

### 弯路 2：读档位表时读到了别的播放器实例

客户端同时挂着多个播放器（信息流预加载、详情页、下一条预载），它们的 `definition.list` 各不相同。
我用 `document.querySelector('video')` / "第一个有列表的播放器"去读，读到的是**预加载那个**（只有 720/540）。

**后果**：同一视频每 1.2 秒在 2K 和 4K 之间来回跳（日志里 `L` 行 `best=-1` / `best=-2` 交替），
用户看到的就是"画质自己跳来跳去、还带着菜单高亮乱跳"。

**教训**：多实例场景必须"认元素"（player.video === 正在播的 video 元素），不能靠"第一个"。

### 弯路 3：播放中强制切流 / reload

```js
p.changeDefinition(tgt)  // 播放中调
p.reload()               // 播放中调
```

**后果**：客户端进入**半切换状态** —— 统计面板显示「码流分辨率 3840×2160 / 分辨率 1920×1080」，
即清单已经按 4K 重建，解码器还在吃 1080 的切片。画面质量和面板数字长期对不上。

**教训**：DASH 的清单在起播时生成，运行中改档由客户端自己决定何时生效；外部强切只会制造不一致状态。

## 四、唯一有效的"显示层"改动

实际在播 4K 时，客户端底部标签还写着「高清 720P」——那是它自己的 UI 状态，与播放无关。
v1.1 加了一个只改文字的模块（每 0.9 秒）：

```
读正在播的 <video>.videoHeight
  ≥2000 → 「超清 4K」   ≥1300 → 「超清 2K」
  ≥1000 → 「高清 1080P」 ≥800  → 「高清 720P」
只写 textContent，不碰播放器
```

## 七、如果还要继续深挖

唯一还没解释的现象：**极少数视频的档位表被裁剪**（feed 数据里有 1080/4K，但播放器列表最高只到 720）。
要定位它需要把 `aweme_id` 和播放器实例关联起来（现在的 dump 里没有 aweme_id），
方法：在 dump 里带上当前视频的 aweme_id（可从 `RENDER_DATA` 或 feed 响应顺序推断），再抽样对照。

在拿到证据前，不建议再动播放器——前面三次弯路都是"没有证据就改"造成的。
