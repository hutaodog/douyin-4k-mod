# PC 高画质起播修复与验证（2026-11-16）

本次修复已安装到本机抖音 PC 客户端 8.8.0。此前实际停在 1920×1080 的同一条视频，现已实际解码为 3840×2160；另一条接口最高为 1440×2560 的视频也已达到该分辨率。验证以当前可见视频的媒体元素、aweme ID、URI 和解码尺寸为依据。

本次继续保留播放安全限制：不在播放过程中循环换源，不重置媒体元素或缓冲，不关闭原生 ABR、卡顿恢复或降档配置。原有 Alt+I、右键详情、只读档位采集和命令结构保留。

## 回归原因与本次修复

2026-11-15 的稳定性修复停用了旧版反复硬换源、补档和抢档路径，避免循环清空缓冲。但同时停用了全部高画质推进路径：部分视频的接口虽然已有高分辨率 HEVC，播放器初始化却选择了最高仅 1080P 的 VVC 编码族。只保留 4K 存储偏好，不能解决这个初始化选择问题。

本次在原始视频数据交给播放器之前，有条件地优选同条视频已有的 HEVC：

1. 本机逻辑处理器数量至少为 8，且 MediaSource 支持 `video/mp4;codecs=hev1.1.6.L93.B0`。
2. 数据具有有效 aweme ID、明确的同视频 URI，且属于非直播视频。
3. 同条视频存在有效 SDR MP4 HEVC 直链；其最大短边大于 1080，并高于该视频 VVC 的最大短边。HDR、DASH 或仅有播放 API 地址的高档不会作为启用依据。
4. 满足条件时，仅从该视频原始 `video.bit_rate` 中排除 numeric2 VVC 候选。原 HEVC/AVC 行、顺序、URL、元数据和低码率档保持原样；条件不满足则不修改。

客户端随后通过自己的初始化路径建立档位表并起播。补丁不将缓存里的其他视频档位补入当前播放器，也不合成新档位。原始档位会在筛选前进入只读采集缓存，便于比较原接口与播放器结果。

当前默认开关：

```text
SAFE_PLAYBACK=true
AB_PATCH=false
QUALITY_AB_PATCH=false
PREFER_HIGH_HEVC=true
REFUSE=none
```

4K 的 `MANUAL_SWITCH` 存储偏好仍每 400ms 维持一次。安全模式的轮询不操作 `src`、`srcObject`、进度或缓冲，也不调用媒体的 `load`、`pause`、`play`。旧的强制换源命令在安全模式下禁用。

曾试验过仅改写三个自动清晰度 AB 参数；同条视频仍停在 1080P，因此该试验没有作为最终方案启用。最终方案不改写服务端 AB 配置，也不伪装编码能力。

## 同视频 4K 对照

目标视频：`7707193655605853931`；URI：`v0d00fg10000dbqn7efog65r3ub3lvag`。

| 项目 | 修复前 | 修复后 |
|---|---|---|
| 实际解码尺寸 | 1920×1080 | 3840×2160 |
| 播放器档位表 | H.266 1080/720/540 | 包含 HEVC 4K/2K，并保留 720/576 |
| 同视频原接口 | 已有 HEVC 3840×2160、2560×1440 | 仍使用该视频原有源 |

原接口 4K 源码率为 2,661,311bps，2K 为 1,753,290bps。本次验证的是达到接口最高分辨率，不等于证明选择了所有同分辨率候选中的最高码率。

连续诊断记录：

- 26 次尝试，24 条有效，2 次命令无响应；有效记录首尾相距 46.401 秒。
- 24 条有效记录均为同一 aweme、同一媒体元素和同一 HTTP 媒体源，实际尺寸始终为 3840×2160。
- 全部有效记录 `readyState=4`，未见暂停或媒体错误；视频时长约 25.06 秒，期间观察到两次自然循环。
- 缓冲余量为 0.204590–24.097123 秒。低缓冲样本当时仍为 `readyState=4`，不能据此推断之后不会卡顿。

原始记录：`work/hevc-init-same-video-4k.jsonl`。两次无响应属于未验证间隙，因此不能把这组记录称为“一分钟无间断播放通过”。

## 验证边界

已验证同视频真实 4K、真实 2K及推荐页短时切换，并消除了补丁的循环硬换源路径。尚未覆盖长时间连续刷推荐、所有视频类型、冷起播计时或受限带宽测试，不能给出启动加速百分比，也不能保证任何网络下永不卡顿。

低码率档和原生 ABR/卡顿恢复配置保留，但带宽不足时是否实际触发降档尚未测量。网络、解码能力、客户端版本或视频数据条件不满足时，实际分辨率仍可能低于接口最高档。当前脚本不会为此重新启用循环硬换源。
