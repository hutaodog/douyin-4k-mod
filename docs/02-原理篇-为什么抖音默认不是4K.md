# 原理篇：为什么抖音 PC 默认不是 4K，为什么看 8 秒就掉档

> 全部结论都标注了**代码位置**或**真机日志**，可自行复核。
> 分析对象：客户端 8.7.0 + 线上 web 包（`lf-douyin-pc-web.douyinstatic.com/obj/douyin-pc-web/ies/douyin_web/`）

---

## 一、先看整体架构：客户端只是壳

```
douyin.exe
  └─ main.dll + __META-INF__/Common.Build-*.node   （主进程，自研序列化打包，非明文）
  └─ resources/app.asar                            （2313 个文件，只有窗口/设置页等外壳）
  └─ resources/app.asar.unpacked/preload.js        （41KB，网页层 preload：注入 TTE_ENV + JSBridge）
        └─ 加载 https://www.douyin.com/             （真正的 UI 与播放器全在网页层）
```

**关键结论：清晰度逻辑 100% 在网页层**，客户端本体不参与。所以我们的注入点只可能是 preload（网页层），这也决定了方案形态。

## 三、清晰度记忆只存在 sessionStorage，而且每次加载会被删

`client-entry~5.46f927bf.js`（模块 389）：

`client-entry~4.e7ecfc84.js`（根布局挂载）：

```js

```

键名（`client-entry~192ceba9`）：

**这就是"关掉重开又回 1080P"的直接原因**：不是没保存，是每次加载主动清空。

## 四、默认为什么是 1080P：ABR 白名单封顶

`async_routes-route.2cc2c67d.js`（`a2` → `as`）：

```js

  ...
  eo = as(aQ(ei,z), z, Q, "h264", Z /* userselection */, false, Y)

as = (list, abtest, awemeInfo, codec, userselection, enableSr, disableBitrateFilter) => {

  } else {

```

默认白名单（`client-entry~6f4ee80d`，偏移 656209~659358）按 `navigator.hardwareConcurrency` 选：

| CPU 核数 | 白名单里最高档 | 实际上限 |
|---|---|---|
| ≤3 | `adapt_lowest_720_1` | 720P |
| 4–7 | `normal_1080_0` | **1080P** |
| ≥8（你的 32 核走这档） | `normal_1080_0` | **1080P** |
| >8 且满足 DT 条件 | `normal_1440_0` | 1440P |

**任何一档都不会自适应到 4K**。所以"直接进推荐页滑动，最高全是 1080P"。

## 六、真正的坑：为什么"看 8 秒会自己掉档"

### 6.1 第一层：服务端 AB 配置里的自动重选

客户端缓存在 **SQLite**：`%APPDATA%\douyin\douyin_app_config` → 表 `app_config` → 键 `abconfig`：

```
auto_clarity_reselect = 1          ← 自动重选清晰度（8 秒那一下的主谋）
switch_clarity_timing = 1          ← 择机切清晰度
smooth_switch_clarity = 1          ← 平滑切清晰度
use_h266_client       = 1
degradeBitrateFactors = [0.5, 0.8] ← 实测码率低于目标 0.5/0.8 倍就降档
abr_config.algoArg.maxDownSwitchLevel = 1
```

> 这个库**每次启动都会被服务端新数据覆盖**（实测：改完 20 秒复查全部回滚），所以不能靠改库。

### 6.2 第二层：清晰度插件的"就近降级 + 延迟 1 秒"

`chunk player-Clarity.bcdc1fa4.js`：

```js
q = () => {
  let t = G(manualSwitch) || {};
  if (t.gearClarity && t.gearClarity !== Auto) {
    let l = A.find(e => e.key === t.gearClarity);        // A = 当前视频的档位列表
    if (!l && A.length > 1) l = 最接近的更低档;           // 找不到就选邻近低档
    ...
    f.definition !== cur.definition && (o(), setTimeout(()=>player.changeDefinition(f,cur), 1000));
    //                                                      ↑ 这 1 秒就是你感知到的"重新加载一下"
  }
}
```

以及列表重建时"取交集"，会把 4K 项交掉：

```js
let e = j({awemeInfo, abtestData, enableDash:false});   // 这次构建没带 userselection
h.list = player.plugins.dashplugin.onPreChangeDefinition(h.list, e.list);
```

### 6.3 第三层：客户端会绕开 `changeDefinition` 直接换流

真机日志（我们给 `changeDefinition` 套了拦截之后）：

```
08:02:15.130  block   blocked downgrade -> 1     ← 拦住了 API 调用
08:02:15.211  media.resize 1080x1920             ← 但媒体流还是被换掉了
08:02:29.450  state   [{"cur":1,"sel":1}]        ← 它还把 1080P 写回 MANUAL_SWITCH
```

**结论：降档不走 `player.changeDefinition`**，播放器内部直接换 `playAddr` / MSE 码流，并且把降档当成"用户的选择"写回存储。所以只拦 API、只塞列表都压不住它。

### 6.4 真机时间线（复现一次）

```
+0.0s  打开视频
+4.1s  2160×3840          4K 正常播放
+4.9s  菜单候选 [超清4K, 超清2K, 高清1080P]
+11.8s 客户端写回 MANUAL_SWITCH（带 clarityReal）
+12.0s 菜单变成 [超清2K, 高清1080P]    ← 4K 项消失
+12.6s 换流 → 1080×1920               ← 掉档
```

## 七、所以正确的解法是什么

不是"改偏好"，而是**关掉那个会主动降档的开关**：

> 在渲染层拦截 `/service/2/abtest_config/` 的响应，把
> `auto_clarity_reselect` / `switch_clarity_timing` / `smooth_switch_clarity`
> 改成 0，并把 `maxDownSwitchLevel` / `rebufferDegrade` 也归零。

真机验证（成功那一次）：

```
08:27:37.642  abpatch  xhr https://www.douyin.com/service/2/abtest_config/ changed=1
（abpatch 共 4 次；block / lost4k / revert 一次都没有 → 客户端根本没再尝试降档）
```

用户确认：**整条视频一直 4K，第 8 秒不再跳 2K。**
