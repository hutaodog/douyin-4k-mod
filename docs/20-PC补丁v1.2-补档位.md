# 20-PC 补丁 v1.2：把被客户端裁掉的档位补回来

> v1.1 只能"在客户端给的档位表里挑"，所以当客户端只挂了 720/540 时无能为力。
> v1.2 找到并解决了这个问题。实测：一条只有 720P 的视频（2K 源）现在稳定 **2560×1440**。

---

## 一、问题长什么样

用户反馈："刷着刷着就全是 720/540"。

日志对比（同一时刻）：

```
接口返回给客户端的档位（我们抓到的）        播放器手里真正的档位表
15 档，最高 2560×1440                       720_2_1@2, 720_3_1@2, 540_3_1@3
  adapt_lowest_1440_1  1440×2560  2509k
  normal_1080_0        1080×1920  2141k
  ...
```

**数据是收到了的，是客户端自己没把高档放进播放器的 `definition.list`。**

而 v1.1 的补丁逻辑是：

```js
var tgt = entryIn(list, CFG.gear);   // 找 4K
if (!tgt || atTarget(cur)) return;   // 找不到就直接 return
```

于是：表里没有 → 什么都不做 → 客户端停在 720。**明明接口给了 2K，我们却因为"找不到 4K"而放弃。**

## 二、逐一排除的假设（都是实测，不是猜）

| 假设 | 实验方法 | 结论 |
|---|---|---|
| 目标档位要太高被服务端裁 | 把 `MANUAL_SWITCH` 改成 1080P 再要 | ❌ 列表仍只有 720 |
| 编码族钉 h264 导致 | 去掉代码族钉住 | ❌ 列表不变 |
| 缺 `channel=channel_pc_web` | 逐参数对照（每次只去掉一个） | ❌ 去掉 channel 仍是 14 档 |
| 缺 `aid=6383` | 同上 | ⚠️ 缺 aid 只剩 5 档，但客户端本来就带了 |
| 主机名 `www-hj.douyin.com` 给裁剪档 | 域名改写 | ❌ 改写后仍 720 |
| `origin_type=quick_player` / `request_source=600` / `support_dash=1` | 逐个加 | ❌ 都是 14 档 |

> 教训：第一轮我以为"缺 channel"，其实我的对照组同时去掉了 `aid`/`device_platform`，**变量不干净**。
> 后来改成"一次只去掉一个参数"才定位准确，并且最终证明参数根本不是原因。

## 三、真正有用的发现：播放器条目 = 接口档位

从客户端播放器里 dump 出一个档位条目的结构：

```json
{
  "vid": "7688690264658939163", "size": 28580177,
  "uri": "v0300fg10000dapqpffog65qtne169d0",
  "url": [{ "src": "https://v11-weba.douyinvod.com/…" }],
  "bitrate": 399, "definition": 2, "qualityType": 12,
  "isH265": true, "gearName": "720_2_1",
  "width": 720, "height": 1280, "format": "mp4",
  "codecType": "h265", "fps": 30, "duration": 47000, …
}
```

它和接口 `bit_rate[]` 的字段是**一一对应**的（`uri` / `url_list`→`url[].src` / `data_size`→`size` / `bit_rate`→`bitrate` / `quality_type`→`qualityType` / `is_h265`→`isH265` / `gear_name`→`gearName`）。

**关键**：`uri` 能把二者对上（同一条视频的所有档位共享这个 uri）。

## 四、v1.2 的三处改动

### 1) 不再钉死编码族

```js
// v1.1: LOCK_CODEC = 'h264'
// v1.2: LOCK_CODEC = ''   （不钉）
```

理由：实测 4K/2K 档（`adapt_lowest_4_1` / `adapt_lowest_1440_1`）**只有 h265**，
而 v1.1 把客户端选的 h265 强行改成 h264 —— 日志里出现 **970 次** `pin codecType=h264 was=h265`。

### 2) 档位表里没有 4K → 改钉该表的最高档

```js
var effTgt = tgt, effDef = CFG.gear;
if (!effTgt) {                       // 没有 4K
  for (...) 找列表里 definition 最小（=画质最高）的条目
  effTgt = bestE; effDef = Number(bestE.definition);
}
if (!effTgt || Number(cur) === Number(effDef)) return;   // 已是最高档则不动
p.changeDefinition(effTgt, p.curDefinition);
```

重试计数也从"同一视频 3 次"改成"视频源 + 目标档位 5 次"，避免一次失败就永久放弃。

### 3) 补档位（核心）

```js
// 抓接口响应里的完整档位，按 uri 索引
captureGears(json) → GEARMAP[uri] = [{def, gear}, ...]

// 每次巡检：播放器列表缺高档就合成条目补进去
fillMissing(list):
  vid   = list[0].uri                        // 这条视频的 uri
  best  = GEARMAP[vid] 里 definition 最小的档位
  if (best.def < 列表里最好的 def) {
      entry = synthEntry(best)               // 按播放器条目结构合成
      list.push(entry);  return best.def;
  }
```

档位映射（来自 `docs/19` 的对照表）：

| 画质 | `definition` | 分辨率（短边） |
|---|---|---|
| 4K | -2 | ≥2160 |
| 2K | -1 | ≥1440 |
| 1080P | 1 | ≥1080 |
| 720P | 2 | ≥720 |
| 540P | 3 | 其他 |

## 五、实测结果

用户实测的那条视频（`7701294669032614565`，@sparkle，哥伦比娅）：

| | 之前 | v1.2 |
|---|---|---|
| 播放器档位表 | `720_2_1@2, 720_3_1@2, 540_3_1@3` | `adapt_lowest_1440_1@-1, adapt_lowest_1080_1@1, 720_x…` |
| 清晰度 | 720P | **`adapt_lowest_1440_1@-1`（2K）** |
| 分辨率 | 1280×720 | **2560×1440** |

其他回归样本（都正常）：

- 4K 视频 → 3840×2160 / 60fps
- 只有 1080P 的视频 → 1920×1080（不再掉 720）
- 只有 540P 的视频 → 576×1024

## 六、一个过程中的自伤 bug（记录一下）

新加的 `captureGears` 那段代码插在了 `var W = window` **之前**，里面用 `W.__dypc4kXxx = ...`，
此时 `W` 是 `undefined` → 抛异常 → **整个播放器锁没启动**（日志里连 `boot`/`state` 都没有）。

改成 `window.xxx = ...` 后恢复。教训：往一个大函数里插代码时，注意它依赖的 `var` 是否已经初始化
（`var` 会提升但值是 undefined，函数声明才会整体提升）。

## 八、还没解决的

- 极少数视频连接口都只给 720（源本身低清），补丁无解
- `fillMissing` 依赖 `list[0].uri` 与接口档位的 `play_addr.uri` 一致；
  如果某些视频两者不一致，注入不会触发（不会出错，只是不生效）
- 清晰度菜单里的勾选项仍可能与实际不符（底部标签已跟随真实分辨率）
