## 坑 1：站点会**在运行时改写 viewport meta**

- 症状：`innerWidth` 时而是 393、时而是 628；页面在 628 布局下渲染"桌面版瀑布流"，播放器高度变 0。
- 证据：`document.querySelector('meta[name=viewport]').content` 被改成 `width=628,initial-scale=0.6258…`（不是我们写的那份）。
- 处理：`guardViewport()` —— 记住"期望值"`vpWant`，用 `MutationObserver` 盯 `content` 属性，被改就立刻改回来；`fitViewport()` 每次重算前先回到窄视口量自然宽度。
- 教训：**用 `innerWidth` 当缩放基准会自激振荡**（缩完 innerWidth 变了 → 下次算出 scale=1 → 又变回宽布局）。基准要固定成 `screen.width`。

## 坑 2：推荐流的播放器在 WebView 里起不来（这是 5/6/7 的真正卡点）

```
url       = https://www.douyin.com/?recommend=1
meta      = width=device-width,initial-scale=1      ← 我们的窄视口生效了
video     = 0×0,  paused=true, readyState=0, 元素 rect 628×0
bodySW    = 628                                      ← 页面自己的排版宽度
```

- 同一路由**从别的页面用 SPA 切过去**时，视频能变成 `1920×1080 / rect 785`（手动验证过）。
- 也就是说：这个页面的播放器初始化依赖它自己的路由挂载时序，冷启动直接进来（或来回切）就不初始化。
- 结论：继续在 WebView 里和它的布局/播放器较劲，投入产出比很低。**原生 feed 才是正解**：
  接口已经验证可用（`aweme/related` 免签、`aweme/detail` 页面内可取全档位），
  播放器已经验证可用（`PlayerActivity` + `HttpMediaSource`，4K HEVC 硬解），
  UI 已经验证可行（`ProfileActivity` 的写法可以照搬）。
