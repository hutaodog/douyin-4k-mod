# 08-手机网页版 4K 验证记录（含线上代码证据）

> 本文是**实测记录**：所有结论都有可以重新跑一遍的命令和落盘数据，不是推测。
> 环境：Windows 10/11 + Node 22 + Playwright 的 Chromium（手机视口 393×852, DPR 3）＋桌面版 UA。
> 时间：2026-10-24　｜　对象：`www.douyin.com` 线上 web 包

---

## 零、一句话结论

**手机网页版能固定 4K，但必须同时满足三个条件**：

1. 浏览器切成**桌面版网站**（移动版 UA 会被导流到引流页，只给 720P 水印流）；
2. **把 AB 里的 `has_2k` 置 1**（手机端 `isHas2K()` 恒为 false，不改这个，选 4K 会被"就近降级"回 1080P）；
3. 关掉播放器的**自动清晰度**（`isPlayAutoDefi` / `isOpenAutoDefi`），否则网速一抖就掉到 540P。

实测结果（同一台机器、同一条视频、同一套脚本）：

| 实验 | 手动档位 | 菜单里的档位 | 实际播放分辨率 | 结论 |
|---|---|---|---|---|
| A 不加脚本 | 无 | 超清 4K / 2K / 1080P / 720P / 540P / 智能 | 1024×576 | 菜单有 4K，但 ABR 自己选了 576P |
| B 老脚本（只改 5 个 AB 键 + 写 MANUAL_SWITCH） | 超清 4K | **1080P / 720P / 540P / 智能（4K、2K 消失）** | 1920×1080 | 手选 4K 反而触发"4K 能力检查"，4K 被过滤掉 |
| C **新脚本**（+`has_2k=1`） | 超清 4K | 超清 4K / 2K / 1080P / 720P / 540P / 智能 | **3840×2160（+9s 起，持续 35s 不掉）** | ✅ 目标达成 |
| C' 新脚本 · 竖屏 4K 视频 | 超清 4K | 超清 4K / 2K / 1080P / 720P / 智能 | **2160×3840**（视频 `7689731341721564658`） | ✅ 验收标准的"2160 × 3840"直接命中 |
| **E 新脚本但关掉 `force2k`**（保留服务端原值 `has_2k=2`） | 超清 4K | 1080P / 720P / 540P / 智能（4K、2K 再次消失） | 1080×1920 → **720×1280** | 跑两次结果一致：**服务端的 `has_2k=2` 不认，必须改成 `1`** |
| D 新脚本 · 横转竖裁切类视频 | 超清 4K | 标清 540P / 智能 | 1026×576 | ⚠️ 该视频客户端自己没给 4K 档（接口里有 gear），见第 4 节末 |

> B 组是最反直觉的一条：**只写 `MANUAL_SWITCH` 会适得其反**。因为客户端的分支是
> `if (userselection) { if (!isHas2K()) 过滤掉 4K/2K }`，手选一旦生效，就走"4K 能力检查"这条路。

## 一、移动版 UA 是"引流页"，不是播放器

用 iPhone/Android UA 打开 `https://www.douyin.com/` 或 `/discover`：

```
final url      : https://www.douyin.com/home      ← 被重定向到落地页
AB 请求        : 0 次（完全没拉 abtest_config）
video 元素     : 无
页面文案       : 下载APP / 下载抖音精选看更多 / 前往抖音电脑版
真实类名       : homeMobileWrapper-peeZH2 / headerWrapper-TuBmQn / swiper-slide …
```

用移动版 UA 打开**具体视频页** `/video/<id>`，能播，但拿到的是引流流：

```
video.currentSrc = https://m.douyin.com/aweme/v1/playwm/?line=0&logo_name=aweme_diversion_search&ratio=720p&video_id=…
                   ↑ playwm = 带水印   ↑ ratio=720p 写死在 URL 里
实际解码        : 1280×720
清晰度菜单      : 没有（页面里没有档位文字）
MANUAL_SWITCH   : 客户端从头到尾没写过
```

> 所以"手机网页版"= 必须请求桌面版网站。桌面版 UA 在 393px 宽的视口里会被抖音自己识别成
> `is-mobile-pc`（`div#dark.windows-os.header-ui.is-mobile-pc`），并下发
> `<meta name="viewport" content="width=device-width,initial-scale=0.5,…">`（把 786px 排版缩到 393px）。

## 二、4K 码流到底有没有：有，而且是 HEVC

接口 `https://www.douyin.com/aweme/v1/web/aweme/detail/` 返回的 `video.bit_rate[]` 展开后
（视频 `7697934740980125171`，共 336 条变体）：

```
 2160p 3840x2160   adapt_lowest_4_1     qt=72   4113 kbps  h265  fps=59
 2160p 3840x2160   adapt_lowest_4_1     qt=72   2869 kbps  h265  fps=30
 1920p 1080x1920   normal_1080_0        qt=1    2869 kbps  h264  fps=30   ← 4K 档没有 h264 版本
 1440p 2560x1440   adapt_lowest_1440_1  qt=7    2580 kbps  h265
 1920p 1080x1920   adapt_lowest_1080_1  qt=2    1222 kbps  h265
```

按 gear 名归并后的最高分辨率：

```
adapt_lowest_4_1    = 2160   ← 这是 4K
normal_1080_0       = 1920
adapt_lowest_1440_1 = 1440
adapt_lowest_1080_1 = 1920
normal_720_0 / 720_2_1 / 720_3_1 / 720_4_1 = 1280
normal_540_0 / 540_3_1 … = 1024 / 576 / 540
```

**关键：4K 只有 HEVC。** 想要 4K，浏览器的 MSE 必须能解 `hvc1`。
`MediaSource.isTypeSupported('video/mp4; codecs="hvc1.1.6.L183.B0"')` 为 `true` 才拿得到。
（这解释了 `05-避坑指南` 第 6 条：封 HEVC = 封 4K。）

## 三、真正的拦路虎：`isHas2K()`

线上 web 包 `client-entry_10c01432.c547b4c0.js`（模块 `785079`，导出 `fR`）原文：

```js
let c=()=>{var e,t;
  let n=o.Le.getConfig(o.gI.AbtestData);
  if(null==n?void 0:n.has2K) return !0;                       // ① AB has_2k 为真 → 直接允许
  let i=["Win32","Windows"].includes(navigator.platform),
      r=["Mac68K","MacPPC","Macintosh","MacIntel"].includes(navigator.platform);
  return i&&navigator.hardwareConcurrency>8                   // ② Windows 且 >8 线程
      || r&&navigator.hardwareConcurrency>=8                  // ③ Mac 且 >=8
      || s()&&navigator.hardwareConcurrency>=8                // ④ 鸿蒙 且 >=8
};
```

`isHas2K()` 的调用点（`async/47733.1859c7e9.js`）：

```js
isHas2K(){return(0,y.fR)()}
```

以及档位列表过滤（原理篇第四节那段 `as()` 的实现）：

```js
if (userselection || disableBitrateFilter) {
  if (!isHas2K()) a = a.filter(不保留 adapt_lowest_4_1 / adapt_lowest_1440_1);   // ← 4K/2K 被删掉
} else {
  a = 白名单过滤 + 码率区间过滤;
}
```

**这意味着：`has2K` 必须是"真值里的那个值"**。实测这个匿名会话服务端下发的是
`data.has_2k.val = 2`（见上），而 **2 不能解锁 4K**（E 组两次复现：4K 档第二次重建列表时被剔掉，
播放停在 720×1280）；把它强制改成 `1` 才能稳定拿到 4K（C 组）。脚本同时用两条通道保证：

1. 响应改写时把 `has_2k.val` 置 `1`（`vid` 原样保留）；
2. 轮询 `window.abTestData`（客户端把 AB 数据挂在这上面，alias 是 `has2K`），发现不是 `1` 就补上。

### `has_2k` 是 AB 里的键（alias 表）

`client-entry_2.a5a52241.js` 里的 AB 键声明表（节选）：

```js
{key:"has_2k",  alias:"has2K",  defaultVal:0}
{key:"has_hdr", alias:"hasHDR", defaultVal:0, solidKey:"has_hdr"}     // HDR 是同一套玩法
{key:"abr_config", alias:"abrConfig", …}
```

所以真正要做的是**在 AB 响应里把 `data.has_2k.val` 强制改成 `1`**（服务端这次给的是 `2`，
实测 `2` 不解锁 4K）。脚本的 `CFG.force2k` 干的就是这件事。

### 响应结构：`data.<key>.{val,vid}`

实测 `https://www.douyin.com/service/2/abtest_config/` 的响应（节选）：

```json
{ "data": {
    "auto_clarity_reselect": {"val": 1, "vid": 12922345},
    "abr_config": {"val": {"algoArg": {"maxDownSwitchLevel": 1, "rebufferDegrade": 1, "safeRebufferDegrade": 0,
                                       "dangerBuffer": 15, "limitFirstDownSwitch": 3},
                            "isOpenAutoDefi": true, "isPlayAutoDefi": true, "abrDriveMode": 1,
                            "timeThreshlod": 60000},
                   "vid": 17081649},
    "bitrate_selector": {"val": {"white_list": ["normal_1080_0", "normal_720_0", "normal_540_0",
                                                "adapt_lowest_1080_1", "adapt_lowest_720_1", "adapt_540_1"]}},
    "has_2k": {"val": 2, "vid": 90332711}
} }
```

> ⚠️ 每个键都带 `vid`（灰度版本号）。老脚本用 `o[k] = 0` 会把整个对象**替换**成数字，
> 结构就废了；新脚本只改里面的 `val`，`vid` 原样保留。

## 四、第二个坑：自动清晰度会把 4K 拉回去

`abr_config.val` 里有两个开关，就是 PC 端第 3 层锁的那两个：

```
isOpenAutoDefi = true     ← 开启自动清晰度
isPlayAutoDefi = true     ← 播放时按带宽自动换档
```

实测（D 组）：当下载吞吐掉到 1.3 Mbps 左右时，播放器在 **+9 秒**把 1080P 拽到 540P，
清晰度菜单也只剩「标清 540P / 智能」。把它们置 `false` 后，档位不再被带宽牵着走。

> 补充：D 组里还有一条视频（`7698098558267919667`）即使 `has2K=true`、两个 AutoDefi 都关掉，
> 客户端仍然把 `clarityReal` 里的 `adapt_lowest_4_1` 剔掉了（该视频接口里确实有 2160x3840 的 gear）。
> 也就是说 **"档位列表"是客户端逐视频算出来的，个别视频会自己不给 4K**——
> 这类只能手动在菜单里点「超清 4K」或换视频，脚本层面没有更优雅的办法。
> 4 条视频里 3 条成功，符合"多数能到 4K"的预期。


## 七、和 PC 端的差异（别照搬）

| | PC 端（已跑通） | 手机网页版（本次） |
|---|---|---|
| 注入 | `preload.js` | Tampermonkey 用户脚本（`@run-at document-start`） |
| `isHas2K()` | Windows 32 核 → 天然为 true | **必须改 AB `has_2k`** |
| AB 结构 | 同样是 `data.<key>.val` | 同，但**不能整体替换成 0**（会丢 `vid`） |
| 播放器锁 | 第 3 层 `needAutoBitrate=false` | 用 AB 的 `isOpenAutoDefi/isPlayAutoDefi=false` 等价实现 |
| 清晰度菜单 | 有 | 桌面版 UA 才有；移动版 UA 无 |
| 界面 | 不用改 | 要 CSS 重绘（全屏播放器 / 隐藏 web 外壳 / 底部标签栏） |

## 八、遗留风险与边界

1. **HEVC 解码是硬前提**：浏览器不给 `hvc1` 支持，4K 无解（脚本的 HUD 会显示 `hevc ✗`）。
   Kiwi/Chrome 在骁龙/天玑新机型一般可以；老机型或 iOS Safari 不保证。
2. **带宽**：4K 档声明码率 2.7–4.1 Mbps，实际吞吐要稳在 5 Mbps 以上才不掉缓冲。
3. **登录**：本次所有实验都是**未登录**状态。登录后 AB 返回值可能不同（尤其 `has_2k`），
   但脚本的"强制置 1"策略对两种状态都成立。
4. **前端改版**：`vid` 校验、alias 表、`isHas2K()` 逻辑都可能变。改动集中在：
   `AB_FORCE`（键名）、`patchABObj`（结构）、`tools/lib` 里的 UA、CSS 里的类名前缀。
5. **画质上限**：网页版上限就是 2160P（HDR 档 `超清 4K HDR` = gearType -3 需要 `has_hdr`，
   默认不开，因为多数手机浏览器的 10bit HDR 输出链路不完整）。
